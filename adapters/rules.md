## Worklog (기록 형식 worklog/2)
명령: `python3 -B "{WL}" <명령> --tool {TOOL}` — 프로젝트 루트에서 실행한다.
- `| NOT_CONNECTED |` 주입이 보이거나 `show`가 "연결되지 않은 폴더"라고 하면: `auto=on`이면 첫 기록 대상 요청에서 아래 작업 결정 규칙대로 주입의 `root=` 폴더에 `new-work "<제목>" --quote "<요청 원문>" --root <root>`를 실행하고(이 명령이 폴더를 연결한다) 그 턴에 save한다. 기록 대상 = 사용자가 결과를 원하는 요청(구현·분석·설계·질문 모두)이며 인사·도구 조작·한 줄 확인은 아니다. `auto=off`면 사용자가 "새 작업: <제목>"이라 할 때만 그렇게 하고, 그 전에는 Worklog 절차(작업 지정 질문·save·skip)를 적용하지 않는다. "<id> 이어서"·"워크로그 켜"에는 연결되지 않았다고 답한다. `new-work`가 `"ok": false`면 기록하지 못했다고 답변에 한 줄로 알리고 요청은 계속한다.
- `| OFF |` 주입이나 .worklog/off가 있으면 작업 지정 질문·save·skip을 하지 않는다. "워크로그 꺼"면 `off --quote "<원문>" [--reason "<이유>"]`, "켜"면 `on` 실행 뒤 skip으로 마친다. 사용자 요청 없이 끄지 않는다.
- 턴 시작: `[Worklog worklog/2 SessionStart` 주입이 보이면 쓰고, 없으면 `show`한다. 대화와 다르면 변경 전에 확인한다. 최초 목표의 값이 바뀌면 유효 결정이 우선한다.
- 기록할 작업 결정: ① 사용자의 명시 지시는 그대로 따른다. "<id> 이어서"는 `use <id> --quote "<원문>"`, "새 작업: <제목>"은 `new-work "<제목>" --quote "<원문>"`, "워크로그 꺼"는 `off`. 작업이 하나뿐이고 "이어서"면 그 작업을 use한다. ② 같은 세션의 현재 작업(주입 `PROVIDED`)은 유지한다. ③ 둘 다 없고 기존 작업이 있으면 요청을 수행하기 전에 "어느 작업에 기록할까요? [목록] / 새 작업"을 한 번 묻고 `skip "작업 지정 대기"`로 마친다. 모델은 기존 작업을 고르지 않는다(최근·유일·내용 유사를 근거로 삼지 않는다). ④ 기존 작업이 하나도 없으면(`auto=on`인 미연결 폴더, 빈 목록) 묻지 않고 새 작업을 만든다. ⑤ 새 작업의 제목은 사용자가 주면 그대로 쓰고, 없으면 요청 내용에서 정해 첫 save summary를 `[auto] 제목 자동: <제목>`으로 시작한다(요청 원문은 quote). 답을 받은 턴에는 `use`/`new-work` 뒤 첫 요청 원문을 quote로 save한다. `use`·`new-work`는 사용자 원문 `--quote`가 없으면 거부된다. `new-work` 결과에 `notice`(다른 작업의 제약은 적용되지 않음)가 있으면 이어받을 제약을 사용자에게 확인한다.
- 작업을 잘못 골랐다고 하면 save 전이면 `use <맞는 id> --quote "<원문>"`, save 뒤면 `reassign <잘못된 id> <맞는 id> --events E0003-E0005 --quote "<원문>"`(사건 범위는 `show`의 목록에서 고른다), 맞는 작업이 아직 없으면 `reassign <잘못된 id> --new "<제목>" --events E0003-E0005 --quote "<원문>"`(새 작업을 만들며 옮긴다), 제목이 틀리면 `rename <id> "<새 제목>" --quote "<원문>"`. 두 작업에 손으로 CORRECTION을 쓰지 않는다. `reassign` 결과가 `"partial": true`면 원인을 고친 뒤 같은 명령을 다시 실행한다.
- 새 작업을 자동으로 만들면 그 턴 답변 끝에 한 줄만 알린다(`기록: <id> 새 작업으로 시작(제목 자동)`). 이후 턴에는 반복하지 않는다.
- `| FORK`가 보이면 본 대화의 곁가지다. 요청을 먼저 수행하고, 첫 기록 대상 요청의 답변 끝에 "이 곁가지의 기록을 어느 작업에 남길까요? [본 세션의 현재 작업 / 목록 / 새 작업]"을 한 번 묻고 `skip "작업 지정 대기"`로 마친다. 지정되면 `use`(또는 `new-work`) 뒤 그 턴부터 스스로 save한다. 지정 전에는 save하지 않는다.
- "기록하지 마"·"워크로그 꺼"는 `off --quote "<원문>"` 실행이다(프로젝트 전체, 원장 밖). "이 파일은 건드리지 마"는 Worklog 기록 금지가 아니라 산출물 제약이다.
- `use` 결과가 현재 상태이므로 그 뒤 별도 `show` 없이 바로 저장할 수 있다.
- 턴 끝: `save`를 한 번 실행한다(stdin JSON). 사용자 요청·결정은 원문 일부를 quote에 넣는다. 제약은 사용자가 바꾸기 전까지 유지한다. 읽기 전용 턴(기록할 변화 없음)은 `skip "이유"`로 마친다.
- 무엇으로 기록할지는 세 질문으로 정한다. ① 사용자가 바꾸기 전까지 모든 턴에 적용되는 금지·자료 범위인가 → `constraints`. 이번 턴에만 적용되는 지시(예: "파일은 만들지 마")는 기록하지 않는다. ② 다음 요청이 오면 저절로 끝나는가 → `waiting`. ③ 지금 고른 방법이나 작업량·목표 범위(몇 화까지 등)처럼 바뀔 수 있는 선택인가 → `decisions`(바뀌면 `replaces`). 결정 텍스트에는 이유를 한 구절 붙인다(예: `11분으로 변경(집중 유지)`, 비워 두지 않는다). 확인되지 않은 가정은 `waiting`에 `확인 필요: …`로 둔다. 에이전트 운영 지시(도구·서브에이전트·평가기·Hook·Goal·질문 방식·테스트 실행 여부에 대한 "~하지 마/써라")는 제약으로 적지 않는다. 그 턴에 지키고 summary에만 남긴다. 사용자가 "앞으로"처럼 지속을 말하면 제약으로 적는다. "무엇을 먼저 보라"는 안내(기준 문서·시작점)는 decisions 텍스트 앞에 `Map:`을 붙인다.
- `status`는 사용자가 작업이 끝났다고 말하기 전까지 COMPLETED로 바꾸지 않는다. 이번 요청이 끝난 것은 `next_action`·`waiting`에 적는다.
- 작업을 COMPLETED로 바꾸는 턴이나 사용자가 "앞으로 이 프로젝트에서는 …"이라고 말한 턴에, 다른 작업에도 적용될 결정·제약이 있으면 ".worklog/project.md에 넣을까요? 쓸 줄: `- [P#] 본문 (worklog:<프로젝트>/<작업>#E… · 날짜)`"처럼 쓸 줄을 보여 주고 한 번 권유한다. 사용자가 "넣어"라고 하기 전에는 project.md를 쓰지 않는다.
- 결정·제약에는 출처가 붙는다. `[사용자]`는 사용자 발언(REQUEST·APPROVAL·D_USER), `[모델]`은 모델 판단(D_AGENT 등). 모델이 스스로 정한 것은 D_AGENT로 남기고 사용자 발언으로 꾸미지 않는다. 사용자 발언과 같은 턴에 모델이 제안한 것(시간 배분 등)은 그 decisions 항목에 `"source": "model"`을 붙인다. `[사용자]` 제약은 사용자 원문 quote가 있어야 해제되고, `[모델]` 제약은 사유만으로 해제한다. 사용자가 모델의 일하는 방식을 바로잡으면 summary 첫머리에 `[behavior]`를 쓰고 사용자 원문을 quote에 넣는다. type은 교정만 남기면 CORRECTION, 지속 제약이나 결정도 함께 넣으면 D_USER다(CORRECTION이 넣는 제약은 [모델] 출처가 되어 사유만으로 해제된다). 작업 내용의 정정은 접두 없는 CORRECTION이다.
- 산출물 save에는 artifacts와 check를 넣는다. check는 유효 결정·제약마다 **규칙이 지켜졌음을 보여 주는 산출물 본문 구절**을 4자 이상 따옴표로 인용한다. 인용할 구절이 없으면 `미반영: 이유`를 적는다. 작업 방식 제약(스케줄러·알림·전달 방식 등)과 그림·압축 파일처럼 인용할 수 없는 것은 미반영이 정상이다. "행동으로 지켰다"는 본문 반영이 아니다. `[Worklog 산출물 없음]`(결과의 `artifacts_missing`)은 사용자에게 한 번 알리고, 옮겼다고 확인하면 `artifacts_moved`, 지웠다고 확인하면 `artifacts_gone`으로 적되 브랜치 전환·되감기처럼 돌아올 파일은 적지 않는다.
- **규칙·제약 문장을 산출물 본문에 써 넣지 않는다(일부만 바꿔 써도 같다).** 그대로 인용하면 결과의 `self_quoted`에 표시되며 반영의 증거가 아니다. "제약을 반영해 달라"는 요청은 본문이 제약을 어기지 않게 쓰라는 뜻이며, 작업 방식 제약은 `미반영: 작업 방식`으로 적는다.
- 위임(서브에이전트): 같은 세션 안의 서브에이전트에 일을 맡기면 **지정받은 세션이 같은 턴에 save**한다. 위임 프롬프트에 "Worklog 명령(use·save·skip)은 실행하지 않는다"를 넣는다. summary 첫머리에 `[delegated: <시킨 일>]`을 쓰고(결정·제약 글자에는 쓰지 않는다), 서브에이전트가 만든 파일은 artifacts+check로, 제안한 결정은 `"source": "model"`로 적는다.
- 위임(별도 세션): 별도 세션은 어떻게 열든(터미널 분할·에이전트 관리 도구·CLI 한 줄 실행 모두 같다) 작업 루트에서 열고 첫 프롬프트를 `"<작업 id> 이어서. 하위 작업: <이름>"`으로 시작한다. 그 도구에 Worklog가 없어도 같은 첫 줄을 쓴다. 금지문은 넣지 않는다(하위 세션이 스스로 save한다). 같은 목표면 같은 작업 id를 쓰고, 따로 완료 처리할 독립 목표나 다른 프로젝트 폴더에 맡기는 일은 `새 작업:`으로 만들며 summary에 상위 작업을 `worklog:<프로젝트>/<작업>#E…`로 적는다. 하위 세션이 도는 동안 그 작업에 save하지 않고(skip), 끝나면 `show`의 '못 본 사건' 절에서 하위 세션의 사건을 확인하고 채택 여부를 `[delegated: <시킨 일>] E0012, E0014`처럼 그 사건 id와 함께 save한다. 다른 프로젝트 폴더의 하위면 `worklog:<프로젝트>/<작업>#E…`로 적는다. 독립 목표를 `새 작업:`으로 맡긴 턴은 상위 작업에 `[delegated: <시킨 일>] 별도 작업 <id>로 맡김`을 save해도 된다(선택). 그 뒤 하위가 도는 동안 두 작업 모두 save하지 않는다. 독립 목표를 맡길 때는 하위 프롬프트에 이어받을 결정·제약을 적는다(없으면 "없음"). 하위 세션은 그것을 사용자 지시로 보고 승계 여부를 다시 묻지 않는다. 메인 세션은 하위(곁가지 포함)의 사건을 id로 인용해 채택만 한다. '못 본 사건' 절에 보이지 않는다는 이유로 내용을 다시 적지 않는다(절은 최근 20건만 보이고 이미 본 사건일 수 있다). 하위가 기록했는지 확인할 수 없으면 `show --work <id>`로 확인하고, 그래도 없으면 대신 save하고 "하위 세션 기록 없음"을 적는다.
- "기록이 바뀌었습니다" 거부면 `show` 후 재저장한다. "현재 작업이 없습니다" 거부면 사용자에게 작업 지정을 요청한다. Stop 차단이면 save 또는 읽기 전용 skip 후 마친다. 다른 거부도 메시지대로 고친다. save·skip 결과에 `warning`(Hook 미작동 의심)이나 `warning_install`(규칙 사본이 오래됨, 설치기 재실행 필요)이나 `warning_worktree`(git worktree 안, 기록이 본 저장소와 갈라짐)가 있으면 사용자에게 알린다. 코어 소스는 읽지 않는다.
